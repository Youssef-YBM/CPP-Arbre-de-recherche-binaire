\section{Résumé}
Ce travail étudie un arbre de recherche binaire (ABR) implémenté en C++.
Le programme mesure le temps total d'insertion, de recherche et de
suppression pour neuf tailles d'entrée, comprises entre $1\,000$ et
$1\,000\,000$ valeurs. Toutes les valeurs testées ont été retrouvées.
Les résultats sont des mesures réelles d'une exécution par taille, et non
des moyennes de plusieurs répétitions.

\section{Protocole de mesure}
Le programme construit les entiers de $0$ à $n-1$, les mélange, puis
chronomètre les trois opérations avec \texttt{std::chrono::steady\_clock}.
La recherche porte sur les mêmes valeurs que celles insérées : ce sont
donc des recherches réussies. Les durées sont des temps cumulés en
millisecondes pour les $n$ opérations. Le parcours écrit dans
\texttt{output.txt} est effectué hors des intervalles chronométrés.

Le programme a été compilé sans option d'optimisation explicite avec
\texttt{g++ -std=c++17 -Wall -Wextra -pedantic}. Les neuf tailles ont été
testées successivement dans le même lancement ; chaque taille correspond
à un nouvel arbre et à un ordre de valeurs mélangé.

\section{Structure et règle de l'arbre}
Chaque élément, appelé \emph{noeud}, contient une valeur et deux pointeurs :
\texttt{gauche} et \texttt{droite}. Pour chaque noeud, toutes les valeurs
du sous-arbre gauche sont plus petites que sa valeur et celles du sous-arbre
droit sont plus grandes. Cette règle permet de choisir une seule branche
à chaque étape d'une recherche.

\begin{lstlisting}
struct Noeud {
    int valeur;
    Noeud* gauche;
    Noeud* droite;

    Noeud(int nouvelleValeur) {
        valeur = nouvelleValeur;
        gauche = nullptr;
        droite = nullptr;
    }
};
\end{lstlisting}

\section{Insertion}
L'insertion commence à la racine. Si le pointeur courant est nul, on crée
un nouveau noeud à cet emplacement. Sinon, on compare la valeur à insérer
avec celle du noeud courant : une valeur plus petite continue à gauche,
une valeur plus grande continue à droite. Dans cette implémentation, une
valeur déjà présente n'est pas ajoutée une deuxième fois.

\begin{lstlisting}
Noeud* inserer(Noeud* racine, int valeur) {
    if (racine == nullptr)
        return new Noeud(valeur);

    if (valeur < racine->valeur)
        racine->gauche = inserer(racine->gauche, valeur);
    else if (valeur > racine->valeur)
        racine->droite = inserer(racine->droite, valeur);
    else
        cout << "Cette valeur existe deja dans l'arbre.\\n";

    return racine;
}
\end{lstlisting}

La fonction est récursive : chaque appel traite un niveau supplémentaire
de l'arbre. Le pointeur de racine retourné permet de conserver la racine
initiale, ou de recevoir le nouveau noeud lorsqu'on insère dans un arbre
vide. Le benchmark génère des valeurs distinctes, donc le cas des doublons
n'intervient pas dans ces mesures.

\section{Recherche}
La recherche compare la valeur cherchée au noeud courant. Une égalité
signifie que la valeur est trouvée. Sinon, la comparaison dirige la
recherche vers le sous-arbre gauche ou droit. Si le pointeur devient nul,
la valeur n'existe pas dans l'arbre.

\begin{lstlisting}
bool rechercher(Noeud* racine, int valeur) {
    if (racine == nullptr)
        return false;
    if (valeur == racine->valeur)
        return true;
    if (valeur < racine->valeur)
        return rechercher(racine->gauche, valeur);
    return rechercher(racine->droite, valeur);
}
\end{lstlisting}

La recherche du test est favorable au sens où chaque requête correspond à
une valeur présente. Le temps rapporté est le cumul de $n$ appels, dans
l'ordre mélangé des valeurs, et non la durée d'une seule recherche. La
suppression reprend ensuite cette même liste mélangée.

\section{Suppression}
La suppression conserve la règle de classement de l'ABR et distingue trois
cas :
\begin{enumerate}
    \setlength{\itemsep}{0pt}
    \item \textbf{Aucun enfant :} le noeud est supprimé et remplacé par nul.
    \item \textbf{Un seul enfant :} le noeud est supprimé et son enfant prend
    sa place.
    \item \textbf{Deux enfants :} la valeur du noeud est remplacée par son
    successeur, le minimum du sous-arbre droit ; ce successeur est ensuite
    supprimé à son emplacement d'origine.
\end{enumerate}

\begin{lstlisting}
Noeud* supprimer(Noeud* racine, int valeur) {
    if (racine == nullptr) return nullptr;
    if (valeur < racine->valeur)
        racine->gauche = supprimer(racine->gauche, valeur);
    else if (valeur > racine->valeur)
        racine->droite = supprimer(racine->droite, valeur);
    else if (racine->gauche == nullptr) {
        Noeud* droite = racine->droite;
        delete racine;
        return droite;
    } else if (racine->droite == nullptr) {
        Noeud* gauche = racine->gauche;
        delete racine;
        return gauche;
    } else {
        Noeud* min = trouverMinimum(racine->droite);
        racine->valeur = min->valeur;
        racine->droite = supprimer(racine->droite, min->valeur);
    }
    return racine;
}
\end{lstlisting}

\section{Affichage et gestion de la mémoire}
Le parcours \emph{gauche--racine--droite} affiche les valeurs en ordre
croissant. Pendant le test, le résultat est dirigé vers \texttt{output.txt}
pour éviter d'imprimer jusqu'à un million de valeurs dans le terminal.
Après le benchmark, les valeurs du test sont supprimées ; la fonction
\texttt{libererArbre} libère également les noeuds restants avec \texttt{delete}.

\section{Chronométrage}
Pour chaque opération, le programme lit l'heure juste avant la boucle et
juste après. La différence avec \texttt{steady\_clock} donne une durée
monotone, exprimée en millisecondes. Les générations, le mélange et
l'écriture du fichier ne sont pas inclus dans les intervalles chronométrés.
En revanche, la création et la destruction des noeuds font partie des
temps d'insertion et de suppression, comme dans le code testé.

\section{Interprétation et limites}
Sur cette série, les durées augmentent globalement avec la taille de l'entrée.
Pour un million de valeurs, l'insertion prend $975,218$ ms, la recherche
$845,118$ ms et la suppression $909,071$ ms. À taille égale, la recherche
est ici la plus rapide pour les grands tests. Une opération d'ABR dépend
toutefois de la hauteur $h$ de l'arbre : son coût est $O(h)$. Un arbre
équilibré donne une hauteur proche de $\log_2(n)$, tandis qu'un arbre très
désequilibré peut atteindre une hauteur de l'ordre de $n$.

Les valeurs sont mélangées, mais l'ABR n'est pas auto-équilibré. Les temps
dépendent donc de l'ordre aléatoire, de l'environnement logiciel et de la
charge de l'ordinateur. Une seule exécution par taille ne permet pas de
calculer une moyenne ni de conclure à une loi de croissance exacte. Pour
renforcer l'étude, répéter chaque taille plusieurs fois, puis comparer la
médiane et la moyenne.

\textbf{\color{bleu}À noter :} la carte graphique n'intervient pas dans cet
algorithme séquentiel ; le benchmark sollicite principalement le processeur
et la mémoire.

\section{Comparaison : recherche binaire et \texttt{std::map}}
Une seconde expérience compare la recherche binaire dans un
\texttt{std::vector} trié à la recherche par \texttt{std::map::find}.
Le menu propose deux ordres d'entrée : valeurs croissantes ou valeurs
mélangées. Les requêtes utilisent le même ordre que les insertions dans
chaque scénario. Le mélange est reproductible grâce à une graine fixe.

Pour le vecteur, le temps de préparation comprend la copie des valeurs et
leur tri ; le temps de recherche comprend $n$ appels à
\texttt{std::binary\_search}. Pour la map, le temps de construction comprend
$n$ insertions dans un \texttt{std::map<int, bool>}, et le temps de recherche
comprend $n$ appels à \texttt{find}. Les durées de construction et de
recherche sont mesurées séparément. Chaque scénario a retrouvé toutes ses
valeurs.

\subsection{Interprétation}
Dans ces mesures, le vecteur trié est plus rapide en recherche que
\texttt{std::map} dans les deux ordres, en particulier pour le scénario
aléatoire à un million d'éléments. La recherche binaire divise l'intervalle
de recherche par deux à chaque comparaison et a une complexité
$O(\log n)$. La recherche dans \texttt{std::map} est également
$O(\log n)$, mais ses noeuds sont répartis dynamiquement et la navigation
par pointeurs a un coût pratique plus élevé ici.

La préparation du vecteur inclut le tri, mais ce coût n'est pas ajouté au
temps de recherche du graphique. Le tableau permet donc de distinguer
construction et requêtes. Pour une utilisation où les données sont
construites une fois puis recherchées souvent, ces deux phases doivent
être interprétées séparément. Les résultats restent ceux d'une exécution
par scénario et peuvent varier avec le système et le compilateur.

\textbf{\color{bleu}Compilation utilisée :}
\texttt{g++ -std=c++17 -Wall -Wextra -pedantic} (sans option
\texttt{-O} d'optimisation explicite).
